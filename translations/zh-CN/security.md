# 安全地运行 Pi

应将模型生成的命令和代码视为不可信内容。Pi 能够以启动它的账号所拥有的权限，读取、修改和执行文件，而且不会在每次工具调用前都请求批准。除非操作系统或虚拟化边界加以限制，扩展、包安装器、语言服务器及其他子进程也都以相同权限运行。

文件、注释、指令、命令输出和模型响应，都可能通过提示注入影响模型。项目信任机制控制启动时加载哪些项目资源，却不能保证这些内容及由此产生的操作是安全的。

安全保障来自对 Pi 可访问、可影响的文件、凭据、进程和网络服务加以限制，以减轻错误或恶意生成操作的影响。查看对话记录、使用项目信任和审查修改，并不会建立安全边界。

## 选择 Pi 的运行方式

不同运行方式，会对生成命令能够访问的范围施加不同限制：

| Pi 的运行方式 | 仍然受到保护的内容 |
|---|---|
| 直接运行，使用其操作系统用户的权限 | 该用户无法访问的任何内容。专用用户账号可以缩小权限范围，但 Pi 仍与其他用户共享操作系统和网络。 |
| 完全在容器、虚拟机或沙箱中运行 | 未向环境开放的宿主机文件和进程。如果将凭据与网络服务提供给环境，它们仍然可以被访问。这通常是实际可行的最强隔离方式。 |
| Pi 运行在隔离环境之外，仅将内置工具放在隔离环境中运行 | 通过这些工具执行的操作无法访问受保护的宿主机资源。Pi 自身和其他扩展仍处于边界之外，因此这种隔离范围较窄。 |

工作目录控制资源发现和工具默认操作位置，但不会阻止命令访问 Pi 进程有权访问的其他路径。

无论选择哪种方式，都只应提供任务所需的文件和服务。尽可能将凭据保留在环境之外，或使用权限范围有限、有效期较短的凭据。命令无需联网时，应限制网络访问。

各隔离方式的配置说明与局限，请参阅[在隔离环境中运行 Pi](containerization.md)。

## 理解项目信任

项目信任控制 Pi 是否加载工作目录提供的大多数设置和资源，防止某个目录在你批准之前悄悄加载可执行扩展。

项目信任并不是完整的启动边界。Pi 在选择或创建会话时，会先读取项目的 `sessionDir` 设置，然后才确定项目信任状态。拒绝信任会阻止其余项目设置和受保护资源加载，但无法撤销最初的会话目录查找。

项目信任不限制工具调用能够访问或影响什么。Pi 启动后，已启用的工具仍使用 Pi 进程的操作系统权限。目录中的指令与其他内容，也可能影响模型。

### 受项目信任保护的资源

Pi 在当前工作目录中发现以下任意资源时，需要作出项目信任决策：

- `.pi/settings.json`
- `.pi/mcp.json`
- `.pi/extensions`、`.pi/skills`、`.pi/prompts` 或 `.pi/themes`
- `.pi/SYSTEM.md` 或 `.pi/APPEND_SYSTEM.md`
- 当前目录或父目录中的项目 `.agents/skills`

仅有一个空的 `.pi` 目录，不需要项目信任。

授予项目信任后，Pi 可以加载：

- 项目设置
- `.pi/mcp.json` 中的项目 MCP Server
- `.pi` 下的扩展、技能、提示模板、主题和系统提示文件
- 项目设置中配置但尚未安装的包
- 项目本地扩展及项目包中的扩展

拒绝项目信任会跳过这些受保护资源，但上文所述的初始 `sessionDir` 查找除外。

除非禁用上下文加载，否则 `AGENTS.override.md`、`AGENTS.md` 和 `CLAUDE.md` 等上下文文件，无论项目信任状态如何都会加载。即使拒绝了项目信任，也应将目录中的指令视为不可信输入。

### Pi 如何作出信任决策

命令行的 `--approve` 或 `--no-approve` 覆盖选项优先应用。存在受保护资源、但没有命令行覆盖选项时：

1. 用户级和命令行扩展可以处理 `project_trust` 事件。第一个返回“是”或“否”的扩展决定结果。
2. 如果没有扩展作出决定，Pi 查找当前目录或其父目录已保存的决策，采用距离最近的一个。
3. 如果没有适用的已保存决策，Pi 遵循全局 `defaultProjectTrust` 设置，其默认值为 `"ask"`。

已保存决策使用规范化目录路径，存放于：

```text
~/.pi/agent/trust.json
```

使用 `/trust` 保存决策，供今后的 Pi 进程使用。

### 没有交互提示时的项目信任

Print、JSON 和 RPC 模式无法显示内置信任提示。如果命令行覆盖选项、扩展和已保存决策都不适用：

- `defaultProjectTrust: "always"` 会加载受保护的项目资源。
- `defaultProjectTrust: "ask"` 或 `"never"` 会跳过这些资源。

自动化运行需要明确的一次性决策时，请使用 `--approve` 或 `--no-approve`。

## 降低影响并改善恢复能力

以下做法不能替代隔离，但能够减少暴露范围，或让恢复更加容易：

- 只让 Pi 访问任务所需的文件和服务。
- 重大修改前使用快照、备份或版本控制。
- 加载扩展和包之前先进行审查。扩展在 Pi 进程内部执行。
- 优先使用权限范围有限、有效期较短的凭据。
- 将结果应用到其他系统之前，先审查差异和生成内容。
- 导出或分享会话前先检查内容，其中可能包含提示、工具参数、命令输出、文件内容，以及对话中暴露的凭据。

## 报告安全问题

按照仓库的[安全政策](https://github.com/earendil-works/pi/blob/main/SECURITY.md)报告。涉及安全敏感信息的报告，不要创建公开 issue。

本地智能体的预期行为、来自不可信内容的提示注入、没有内置沙箱，以及用户安装的扩展或技能产生的行为，通常不属于安全边界内的问题；除非报告证明存在权限边界绕过，或获得了本地用户原本并不具备的访问权限。
